# Coco 变更控制

开发中收到新反馈时先分类，再修改。目标是持续保持事实一致，但不因每个小细节重跑整个流程。

当前需求/缺陷下的追问、复测和直接相关测试反馈默认沿用原 Work Item，只更新已有记录；不得因为一次测试失败自动创建新的缺陷流程。只有独立问题或用户明确要求单独跟踪时才拆分新缺陷。

## 处理顺序

1. 记录原话、来源、时间、当前基线和相关场景。
2. 判断是实现缺陷、需求调整、未决讨论还是单纯澄清。
3. 评估用户行为、验收、UI、API、DB、权限、安全、运维和测试影响。
4. 分级并确定必须先更新的“指导性内容”。
5. 用户确认方向后修改代码和测试。
6. 当前小批次结束时整理其余受影响文档并关闭变更。

## 等级

- **L0 未决讨论**：只写 `change-log.md`，不改代码，不改正式基线。
- **L1 实现缺陷/澄清**：规格不变；修代码并补回归测试，按需更新验证记录。
- **L2 局部细节**：文案、间距、局部交互或不改变契约的小调整。先更新变更记录和直接受影响的设计/验收/测试条目；无需重做分析、架构和整份计划。
- **L3 行为或契约变化**：用户流程、验收、API、DB、权限、安全或范围改变。暂停相关任务，先更新受影响的需求/设计、计划和测试范围，再实现。
- **L4 目标或架构转向**：重新做影响分析并建立新版本基线；旧任务标记 `Superseded`、`Rework` 或 `Cancelled`。

## 轻量执行

- L1 和不改变行为/契约的 L2 默认走轻量流程：确认影响边界，修改最少文件，执行聚焦回归，报告结果。
- 仅文案、注释或局部视觉且无现有工作项目录时，不强制创建 `change-log.md`。
- L2 一旦改变用户行为、验收、状态流转或响应式规则，升级 L3。
- L3/L4 必须进入完整流程并更新分析、设计、计划和测试范围。

## 最小同步矩阵

- 文案/视觉：产品设计、对应验收和 UI 测试。
- 用户行为：需求、产品设计、计划、测试和验收。
- API/数据/权限：需求或缺陷影响、技术设计、计划、契约/迁移/安全测试。
- 实现缺陷：缺陷证据、代码、回归测试、验证。

## 变更记录

每项使用稳定 ID，例如 `CHG-003`，记录类型、等级、决定、理由、影响、不影响、批准状态、相关任务/测试和验证结果。未确认项不得写入正式基线。

变更记录按需写入 `docs/plans/{Work-Item-Key}/change-log.md`，不要求每个工作项预先创建。

紧急修复若无法先完成文档，只能标为 `Provisional`；同一交付批次必须补齐受影响基线，不能拖到项目结束统一猜测。

## 输出规范

只输出完成任务所需的核心内容；删除客套话、长篇铺垫、重复信息和无关说明。代码、文档和注释保持最小必要范围，不添加冗余注释。需要报告时优先给出结论、变更、验证结果和阻塞项。
