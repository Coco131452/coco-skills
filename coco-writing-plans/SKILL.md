# Coco 编写计划

计划必须让不了解当前上下文的开发者仍能正确执行。先读取工作项基线和实际相关代码；不得从旧设计直接规划。

本技能只用于完整流程。轻量调整或已证明根因的局部低风险缺陷不创建计划；若影响 API、数据、权限、UI 行为、共享模块或测试范围无法快速确定，则升级完整流程并使用本技能。

## 输入优先级

1. 当前用户确认和 `change-log.md` 中已接受的变更。
2. Jira MCP 读取的当前工作项、评论、附件和关联事项（如适用）。
3. Apifox MCP 读取的当前 Server/API 契约（如适用）。
4. 有效的需求/缺陷分析与产品/技术设计。
5. 当前代码、测试和配置。
6. 项目级规范和历史决策。

若来源冲突，列出冲突并暂停受影响任务；低风险缺口可写明假设后继续。

若 `analysis.md` 表明工作项涉及前端，但 UI 设计状态缺失或为 `Provisional`，暂停并提醒用户是否先设计 UI。确认 `Required` 时必须先完成 `coco-product-design` 和原型确认；确认 `Reuse Existing` 或 `Not Applicable` 时记录依据后再编写计划。

## 计划要求

- 明确目标、范围、非范围、依赖、风险和回滚。
- 按垂直切片拆分，每项都有具体文件、行为和可观察结果。
- 新功能和缺陷修复按 RED -> 验证失败 -> GREEN -> 验证通过 -> REFACTOR -> 全量复验描述。
- 覆盖代码、数据、配置、测试、文档、监控和发布中实际受影响的部分。
- 涉及 Jira 时在计划中保留 Issue Key 和来源映射；涉及 Server/API 时将 Apifox 契约校验、兼容性和契约测试拆成明确任务。
- 前端调用接口时，计划必须包含 Apifox MCP 读取任务和接口调用清单；每个生成方法标明调用文件、契约路径、参数、响应和错误处理。
- UI 设计状态为 `Required` 时，计划必须包含页面逻辑判断、状态流转、接口触发时机和原型确认任务；未完成 G2 原型/逻辑确认不得进入实现。
- 每个任务关联需求故事/缺陷证据、验收标准和验证命令。
- 标出可并行项、关键路径以及必须人工确认的 Gate。
- 明确 G2 计划批准点、G3 实现检查点和 G4 交付验收点；每个 Gate 写明负责人、输入材料、批准标准和阻塞处理。
- 不硬编码任务时长、覆盖率或批次大小；优先使用项目策略，否则按风险确定。

## 产物

写入 `docs/plans/{Work-Item-Key}/plan.md`。首次创建后不得覆盖；已有计划使用 `plan-1.md`、`plan-2.md` 等递增文件。L4 重大方向变化同样使用下一个 `plan-{n}.md`，保持递增命名规则。

计划至少包括状态总览、任务、测试映射、执行记录、风险、人工 Gate 和待确认项。任务状态使用 `Pending`、`In Progress`、`Blocked`、`Done`、`Superseded`、`Cancelled`。开发中发生变更时交给 `coco-change-control`，不要私自继续旧计划。

创建计划前读取 [plan-contract.md](references/plan-contract.md)。生成新计划不得覆盖旧计划；执行阶段允许在当前计划文件中维护任务状态和执行记录。

## 输出规范

只输出完成任务所需的核心内容；删除客套话、长篇铺垫、重复信息和无关说明。代码、文档和注释保持最小必要范围，不添加冗余注释。需要报告时优先给出结论、变更、验证结果和阻塞项。
