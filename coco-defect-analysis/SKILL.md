# Coco 缺陷分析

先证明问题，再决定修复。不要从错误信息直接猜根因，也不要把用户在测试中提出的新期望自动归类为缺陷。

## 缺陷或变更

比较实际行为、当前有效基线和用户新期望：违反基线是缺陷；符合基线但新期望改变行为是需求变更；基线含糊时记录争议和复现证据，请用户确认预期。

## 现象与证据

- 环境、版本、角色、权限、数据前置条件。
- 稳定复现步骤、实际结果、预期结果和发生频率。
- 完整日志、堆栈、请求响应、截图、Trace 或数据库状态。
- 首次出现版本、相关 Git 变更及是否为回归。

## 原因分析

- 症状位置、故障边界、调用链和数据流。
- 已验证事实、候选假设及排除证据。
- 直接原因、根本原因和促成因素。
- 为什么现有测试、监控或流程未提前发现。

无法证明根因时写“尚未确认”，不能把最可能的解释当事实。

## 影响分析

- 直接文件、模块、服务、配置和间接调用方。
- API 消费者、共享组件、数据、Migration、缓存和兼容性。
- 页面、业务流程、角色、权限和失败路径。
- 修复范围、非修复范围、发布风险和回滚要求。
- 回归测试、单元、整合、契约、数据库、UI/E2E、Smoke，以及按风险选择的安全、并发、性能和迁移测试。

## 产物

写入 `docs/coco/{id}/defect-analysis.md`，包含证据表、原因树、影响矩阵、测试矩阵、修复选项、风险及待确认项。同步 `index.md`；调查期间为 `Investigating`，根因和范围有证据后才进入计划。
