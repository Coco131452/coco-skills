# Coco 缺陷分析

先证明问题，再决定修复。不要从错误信息直接猜根因，也不要把用户在测试中提出的新期望自动归类为缺陷。

## 外部信息读取

- 提供 Jira Bug/Task 单号或链接时，先使用 Jira MCP 读取 Issue，并按需读取评论、附件和关联单，提取预期行为、环境、历史讨论和验收信息。
- 涉及 Server/API 时，使用 Apifox MCP 刷新并读取最新 OpenAPI 契约，核对路径、方法、参数、Schema、鉴权、响应和错误码。
- Jira、Apifox、代码和运行结果冲突时分别记录“声明行为、契约行为、实现行为和实际行为”，不能仅凭其中一项判断根因。
- 默认只读；更新 Jira 状态、评论、字段或附件必须获得用户明确授权。

## 缺陷或变更

比较实际行为、当前有效基线和用户新期望：违反基线是缺陷；符合基线但新期望改变行为是需求变更；基线含糊时记录争议和复现证据，请用户确认预期。

## 现象与证据

- 环境、版本、角色、权限、数据前置条件。
- 稳定复现步骤、实际结果、预期结果和发生频率。
- 完整日志、堆栈、请求响应、截图、Trace 或数据库状态。
- 首次出现版本、相关 Git 变更及是否为回归。

## 原因分析

- 症状位置、故障边界、调用链和数据流。
- 已验证事实、候选假设及排除证据。
- 直接原因、根本原因和促成因素。
- 为什么现有测试、监控或流程未提前发现。

无法证明根因时写“尚未确认”，不能把最可能的解释当事实。

## 影响分析

- 直接文件、模块、服务、配置和间接调用方。
- API 消费者、共享组件、数据、Migration、缓存和兼容性。
- 页面、业务流程、角色、权限和失败路径。
- 修复范围、非修复范围、发布风险和回滚要求。
- 回归测试、单元、整合、契约、数据库、UI/E2E、Smoke，以及按风险选择的安全、并发、性能和迁移测试。

## 产物

写入 `docs/plans/{Bug-Key}/defect-analysis.md`，包含 Jira/Apifox 引用及读取时间、证据表、声明/契约/实现/实际行为差异、原因树、影响矩阵、测试矩阵、修复选项、风险及待确认项。调查期间为 `Investigating`，根因和范围有证据后才进入 `plan.md`。

创建或维护前读取 [defect-analysis-contract.md](references/defect-analysis-contract.md)。根因、影响矩阵和测试影响作为同一文件的章节，不再拆成多个空文件。
