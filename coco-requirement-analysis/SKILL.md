# Coco 需求分析

把业务意图转为可观察、可验证的需求基线。本技能只负责分析；除非用户同时要求实现，否则不修改产品代码。

## 输入顺序

1. 用户当前表述与附件。
2. 若存在 Jira 单号或链接，使用 Jira MCP 读取 Issue、评论、附件和关联事项。
3. 若涉及 Server/API，使用 Apifox MCP 刷新并读取 OpenAPI 主文档及相关 `$ref`。
4. `docs/plans/{Work-Item-Key}/`、历史变更和现有项目规格。
5. `coco-codebase-index` 结果与实际相关代码、测试。
6. 项目约束、设计系统和运行环境。

索引只用于导航，结论必须回到实际文件验证。

Jira 内容、用户当前说明、Apifox 契约与代码不一致时，在分析中建立“来源差异”小节并请求确认；不得自行覆盖 Jira 或接口契约。Jira 和 Apifox 默认只读，除非用户明确要求同步修改。

## 分析步骤

1. 定义问题、目标用户、使用情境和成功结果。
2. 区分目标、建议方案和不可改变约束，避免把示例误当唯一实现。
3. 建立带稳定 ID 的用户故事及可观察验收标准。
4. 覆盖正常、空、加载、失败、权限、并发及恢复路径中实际适用的部分。
5. 定义功能范围、非范围、P0/P1/P2、依赖和最小可交付切片。
6. 检查安全、隐私、性能、可访问性、审计、兼容和运维要求。
7. 映射可能涉及的页面、接口、模块、数据和测试；标注已验证与待确认。
8. 找出矛盾、隐含需求、风险和需要人类决策的权衡。

只在缺失信息会实质改变范围或架构时逐个提问；可以从代码低风险推断的内容说明假设后继续。

## 产物

写入 `docs/plans/{Story-Key}/analysis.md`：Jira 引用及读取时间（如有）、背景、目标、角色、用户故事、验收标准、范围/非范围、优先级、依赖、Apifox 接口引用（如有）、代码现状、非功能需求、来源差异、风险、假设、待确认项，以及需求到功能/测试的初始追踪表。

创建或维护前读取 [analysis-contract.md](references/analysis-contract.md)，遵循其中的章节、状态和来源标记规则。

在 `analysis.md` 的文档信息中维护状态和有效基线。尚未确认的内容标记 `Provisional`，不得伪装为已批准需求。
