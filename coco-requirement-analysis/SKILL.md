# Coco 需求分析

把业务意图转为可观察、可验证的需求基线。本技能只负责分析；除非用户同时要求实现，否则不修改产品代码。

## 输入顺序

1. 用户当前表述与附件。
2. 若存在 Jira 单号或链接，使用 Jira MCP 读取 Issue、评论、附件和关联事项。
3. 若涉及 Server/API，使用 Apifox MCP 刷新并读取 OpenAPI 主文档及相关 `$ref`。
4. `docs/plans/{Work-Item-Key}/`、历史变更和现有项目规格。
5. 实际相关代码、测试、配置及运行入口。
6. 项目约束、设计系统和运行环境。

若输入来自 Jira，必须先读取 Issue Type 并据此确认本单是 Story/Task 需求还是 Bug/Defect 缺陷；Issue Type 未确认时保持 `Provisional`。

Jira 内容、用户当前说明、Apifox 契约与代码不一致时，在分析中建立“来源差异”小节并请求确认；不得自行覆盖 Jira 或接口契约。Jira 和 Apifox 默认只读，除非用户明确要求同步修改。

## 团队协作门禁

- 有 Jira 输入时，在 `analysis.md` 记录 Issue Key、链接、读取时间、当前状态、负责人、验收标准和附件/UI 示意来源。
- 同时记录 Jira Issue Type 和类型判定依据；不得仅按标题或用户口述改写类型。
- 在产品/需求负责人确认目标、范围、验收标准和来源差异前，状态保持 `Draft` 或 `Provisional`，不得进入正式计划执行。
- 如需回填 Jira 评论，先生成 ADF 草稿；只有用户明确授权且工具支持时才提交。
- 分析结论应输出 G1 待确认项，供人工检查点确认；不得把 AI 推断标记为已批准事实。
- 若前端需要调用接口，在分析中登记“待 Apifox 读取”的接口范围；接口契约和方法清单由技术设计/计划阶段补齐。
- 前端需求必须在 `analysis.md` 记录 UI 设计状态：`Required`、`Reuse Existing` 或 `Not Applicable`。缺少 UI 来源且无法确认复用现有设计时，将状态标为 `Provisional`，提醒用户是否先设计 UI，不得直接进入计划或实现。

## 分析步骤

1. 先用简洁语言输出对 Jira 需求的理解：目标、用户、场景、预期行为、范围和验收标准。
2. 定义问题、目标用户、使用情境和成功结果。
3. 区分目标、建议方案和不可改变约束，避免把示例误当唯一实现。
4. 建立带稳定 ID 的用户故事及可观察验收标准。
5. 覆盖正常、空、加载、失败、权限、并发及恢复路径中实际适用的部分。
6. 定义功能范围、非范围、P0/P1/P2、依赖和最小可交付切片。
7. 检查安全、隐私、性能、可访问性、审计、兼容和运维要求。
8. 映射可能涉及的页面、接口、模块、数据和测试；前端需求同时确认 UI 设计状态及其依据，标注已验证与待确认。
9. 找出矛盾、隐含需求、风险和需要人类决策的权衡。

只在缺失信息会实质改变范围或架构时逐个提问；可以从代码低风险推断的内容说明假设后继续。

## 产物

写入 `docs/plans/{Story-Key}/analysis.md`：Jira 引用及读取时间（如有）、需求理解摘要、背景、目标、角色、用户故事、验收标准、范围/非范围、优先级、依赖、Apifox 接口引用（如有）、代码现状、影响范围、测试范围、来源差异、风险、假设、待确认项，以及需求到功能/测试的初始追踪表。

创建或维护前读取 [analysis-contract.md](references/analysis-contract.md)，遵循其中的章节、状态和来源标记规则。

在 `analysis.md` 的文档信息中维护状态和有效基线。尚未确认的内容标记 `Provisional`，不得伪装为已批准需求。

## 输出规范

只输出完成任务所需的核心内容；删除客套话、长篇铺垫、重复信息和无关说明。代码、文档和注释保持最小必要范围，不添加冗余注释。需要报告时优先给出结论、变更、验证结果和阻塞项。
